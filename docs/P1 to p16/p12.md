# Zolto Phase 12 — Plugin API & Extension System

## Goal

Build a safe, stable, and powerful extension system so Zolto can grow beyond the core language without turning the core into a giant monolith.

This phase gives Zolto a controlled way to load plugins, register new directives, extend renderers, add custom parsers, expose new data sources, and integrate with external tools.

Everything from Phases 1–11 must continue working exactly as before.

---

Create a complete plugin and extension architecture featuring:

* Plugin registration
* Plugin lifecycle
* Extension hooks
* Custom directives
* Custom renderers
* Custom parsers
* Custom validators
* Theme extensions
* Data provider extensions

* Permission control
* Version compatibility
* Plugin metadata
* Discovery system
* Performance isolation

# 1. Plugin Manifest

Implement a standard plugin package format.

Example

```zolto id="plg100"
@plugin
name: "Zolto Todo Plugin"
version: "1.0.0"
author: "Zolto Team"
description: "Adds todo blocks and status tracking."
@/plugin
```

Requirements

* Plugin name
* Version
* Author
* Description
* Compatibility range
* Dependency list
* Permission list
* Entry points
* Metadata fields

* PluginPermission

* Unsafe extension behavior

## Not Included

Do NOT implement:

* IDE/LSP tooling
* Collaboration
* Theme redesign for all core nodes
* Arbitrary code execution
* Unsafe native modules
* Real-time cloud sync

Those belong to later phases or separate security-reviewed systems.

---

# Final Goal

At the end of Phase 12, Zolto should have a robust plugin and extension ecosystem that allows safe growth, third-party add-ons, custom syntax, custom renderers, and external integrations without compromising the stability of the core language.
